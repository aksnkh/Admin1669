# مدیریت ۱۶۶۹ — Admin1669

پروژهٔ React + TypeScript با خروجی استاتیک، بازسازی‌شده از ظاهر و امکانات فایل `dist.rar` ارائه‌شده توسط مالک پروژه. سورس اصلی از روی bundle بازیابی نشده است؛ ساختار جدید برای توسعهٔ مرحله‌به‌مرحله تهیه شده است.

## شروع توسعه

Node.js نسخهٔ 22.12 یا جدیدتر (نسخهٔ 24 نیز پشتیبانی می‌شود):

```bash
npm ci
npm run dev
```

```bash
npm test
npm run build
npm run preview
```

تست مرورگر:

```bash
# Chromium را روی سیستم نصب کنید، یا مسیر مرورگر را مشخص کنید:
CHROMIUM_PATH=/usr/bin/chromium npm run test:e2e
```

تست مرورگر روی خروجی ساخته‌شده اجرا می‌شود؛ پس ابتدا `npm run build` را اجرا کنید. تست‌ها پاسخ API را شبیه‌سازی می‌کنند و هیچ داده‌ای در سرور واقعی تغییر نمی‌دهند.

## خروجی و انتشار

با `npm run build`، پوشهٔ `dist` تولید می‌شود. **تمام محتوای این پوشه** را روی هاست استاتیک IIS، Nginx یا هر وب‌سرور دیگر کپی کنید. Node.js روی سرور انتشار لازم نیست. برای باز کردن برنامه از HTTP/HTTPS استفاده کنید؛ اجرای مستقیم `index.html` با `file://` مناسب نیست.

مسیریابی HashRouter است (`#/orders-report`) و فایل‌ها مسیر نسبی دارند؛ انتشار در ریشه یا یک زیرپوشه نیاز به rewrite مسیرهای React ندارد. محتوای پوشهٔ dist را کامل و در کنار هم قرار دهید. API باید از دامنهٔ سایت اجازهٔ CORS برای `POST`، `Content-Type` و `Authorization` بدهد. سایت HTTPS باید به API HTTPS متصل شود.

آدرس API را در `public/config.js` پیش از build یا `dist/config.js` بعد از build ویرایش کنید:

```js
window.ADMIN1669_CONFIG = {
  apiBaseUrl: 'https://api.alobegoo.com/api',
  referralEndpoint: 'Orders/refDataEntryForMobile',
};
```

این فایل **عمومی** است و نباید رمز، توکن، connection string یا کلید امضای JWT داشته باشد. برای تغییر مقصد API نیازی به build دوباره نیست. روی هاست برای `config.js` و `index.html` سیاست cache کوتاه یا revalidation تنظیم کنید. فایل‌های نام‌گذاری‌شده با hash در `assets` می‌توانند cache طولانی داشته باشند. سرویس‌ورکر نسخهٔ قبلی در این بازسازی منتقل نشده؛ نصب PWA و کار آفلاین جزو این نسخه نیست.

## صفحات

- ورود با نام کاربری و رمز، نمایش/پنهان‌سازی رمز و نمایش خطا.
- پیشخوان و دسترسی به گزارش و ارجاع.
- گزارش سفارش‌ها: فیلترهای سمت سرور مطابق API، صفحه‌بندی، جزئیات کامل سفارش و CSV همان صفحه.
- ارجاع: کارت سفارش، تماس با مشتری، فهرست تکنسین‌های تحت نظارت، انتخاب و تأیید نهایی ارجاع.
- نسخهٔ نمایشی با داده‌های کاملاً نمونه، بدون تماس با API و بدون ثبت ارجاع؛ از دکمهٔ «مشاهده نسخه نمایشی» در ورود در دسترس است.
- رابط فارسی راست‌به‌چپ، سازگار با موبایل و دسکتاپ.

## قرارداد API

تمام مسیرها نسبت به `apiBaseUrl` هستند. API مقصد `PwaApi1669` است، نه پروژهٔ قدیمی `Api`.

| عملیات            | درخواست POST                                       | پاسخ                      |
| ----------------- | -------------------------------------------------- | ------------------------- |
| ورود              | `auth/login`، `{ userName, password }`             | `TokenPair` مستقیم        |
| تمدید نشست        | `auth/refresh`، `{ refreshToken }`                 | `TokenPair` مستقیم        |
| خروج              | `auth/logout`، `{ refreshToken }`                  | HTTP 204                  |
| سفارش‌ها          | `Orders/selDataEntryForTechnician`                 | `Response<Order[]>`       |
| تکنسین‌های سرپرست | `Tch/getSprTch`، بدون بدنه                         | `Response<Technician[]>`  |
| استان‌ها          | `BasicInfo/getProvince`، بدون بدنه                 | `Response<{ prvName }[]>` |
| ثبت ارجاع         | `Orders/refDataEntryForMobile`، `{ id, ref_tech }` | `Response<bool>`          |

`TokenPair` شامل `accessToken`, `refreshToken`, `accessTokenExpiresAtUtc`, `refreshTokenExpiresAtUtc` است. نام خصوصیات پاسخ camelCase مطابق تنظیمات پیش‌فرض ASP.NET Core در نظر گرفته شده است. پاسخ‌های فهرست‌ها ساختار `{ statusCode, message, title, payload }` دارند.

فیلترهای گزارش دقیقاً `ID`, `CustomerID`, `CustomerFamily`, `Technician`, `Mobile`, `Date`, `Tel`, `Province`, `Ref`, `PageNo`, `PageSize` هستند. فیلتر تکنسین **نام کامل** را ارسال می‌کند؛ شناسهٔ تکنسین ارسال نمی‌شود. فیلترهایی مثل برند، دستگاه، شهر یا بازهٔ تاریخ که در قرارداد فعلی سفارش‌ها نیستند، به‌عنوان فیلتر سرور نمایش داده نمی‌شوند. این ستون‌ها در جزئیات قابل مشاهده‌اند. قالب/تقویم مقدار `Date` باید با پروسیجر SQL هماهنگ باشد؛ فرانت تبدیل تقویم انجام نمی‌دهد.

**ثبت ارجاع:** قرارداد فوق با مالک پروژه تأیید شده است؛ پیاده‌سازی و انتشار endpoint بک‌اند بر عهدهٔ ادامهٔ کار بک‌اند است. UI تنها پس از دریافت `payload: true` موفقیت را نشان می‌دهد. برای غیرفعال‌سازی موقت، `referralEndpoint` را `null` کنید. نام کاربر در `getSprTch` از JWT در بک‌اند گرفته می‌شود؛ کاربر نمی‌تواند Username دلخواه در بدنه ارسال کند.

توکن‌ها فقط در `sessionStorage` همان برنامه نگهداری می‌شوند. درخواست‌های 401 یک‌بار با refresh خودکار تکرار می‌شوند؛ تمدیدهای همزمان در هر پنجره serialize می‌شوند. رمز ورود ذخیره نمی‌شود. خروج فقط کلید نشست این برنامه را پاک می‌کند و لغو refresh token را به API درخواست می‌دهد. داده‌های حساس API برای حالت آفلاین cache نمی‌شوند.

مقادیر عددی خروجی مانند CustomerID، Cost و OfflineID می‌توانند از Int32 بزرگ‌تر باشند. JavaScript اعداد صحیح را تنها تا `Number.MAX_SAFE_INTEGER` دقیق نگه می‌دارد؛ برای پشتیبانی از تمام محدودهٔ SQL bigint باید بک‌اند شناسه‌ها را رشته برگرداند. شناسهٔ ورودی بزرگ‌تر از محدودهٔ امن در رابط رد می‌شود.

## ساختار

```text
src/api/          کلاینت HTTP، مدیریت توکن و قراردادهای سفارش
src/components/   قالب اصلی و اجزای مشترک
src/pages/        ورود، پیشخوان، گزارش و ارجاع
src/types.ts      قراردادهای ورودی و خروجی
src/demo.ts       داده‌های نمونه
public/config.js  تنظیمات زمان اجرا
public/assets/    تصاویر برگرفته از فایل ارائه‌شده
public/fonts/     فونت ارائه‌شده و اعلان اصلی مجوز
```

تصاویر و فونت از فایل ارسالی مالک پروژه گرفته شده‌اند. اعلان مالکیت فونت در `public/fonts/NOTICE.txt` حفظ شده است؛ انتشار این دارایی‌ها تابع مجوزهای پروژهٔ اصلی است. bundle جاوااسکریپت، توکن‌ها و فایل‌های association/شناسهٔ اپلیکیشن نسخهٔ قبلی کپی نشده‌اند.

## وضعیت اعتبارسنجی

Build TypeScript و Vite، تست‌های واحد و تست‌های مرورگر با API شبیه‌سازی‌شده اجرا می‌شوند. اتصال واقعی به API، CORS دامنهٔ انتشار، نام کاربری/رمز واقعی و ثبت ارجاع واقعی نیازمند سرور و حساب معتبر هستند و توسط این تست‌ها اثبات نمی‌شوند. درخواست خواندن Swagger سرور از محیط توسعه با پاسخ 403 پراکسی شبکه مسدود شد؛ این نتیجه به‌تنهایی وضعیت خود سرور را مشخص نمی‌کند.

GitHub Actions در push و pull request تست واحد و build را اجرا و خروجی `dist` را به‌صورت artifact نگه می‌دارد؛ انتشار سایت خودکار انجام نمی‌شود.
